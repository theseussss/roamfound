## §0 · 涌现期纪律

产品原型文档不是一开始就有结构的。常见生长路径：**碎片条目 → 主题聚合 → 骨架浮现**。早期**内容优先于结构**——别硬套下文骨架模板。骨架是事后命名，不是前置契约。

自检一次：现在这份 vision 更像条目还是骨架？条目期继续让它生长，不必强求成形。

**与 SKILL.md §2.1 话题的对接**：§2.1 话题纪律"结构优先于内容"**针对已有可维护 TOC 的话题**（card 级已沉淀）。本节例外适用于 Vision 基础话题卡（SKILL.md §3.2 初始化时创建，承载项目方向与验收标准）的早期生长阶段。两个纪律不矛盾，是不同生命阶段的默认顺序。

## §1 · 为什么需要骨架

**目标清晰即实现**——对目标的精确描述本身就是实现目标的过程乃至是目标本身。

骨架（已有的理论模板）的作用不是"正确答案"，是**减少空白页焦虑**与**促进完备性**：
- 填到某个字段发现空了 → 发现一个没想清楚的维度
- 对比多个骨架 → 逼出多视角
- 骨架之间的字段互斥/补充关系本身是思考工具

不强求完整填完。骨架是**生长方向**，不是**验收硬条件**。

## §2 · 成熟阶段参考 · 五骨架

每个骨架给：来源 / 字段结构 / 适用场景 / 最小示范 / 何时不适用。

### 2.1 PRD · 产品需求文档（软件）

- **来源**：软件工程工业实践（Google / Meta / Atlassian 等公司模板）
- **字段结构**：
  - 产品定位（对谁，解决什么核心问题）
  - 核心能力（MVP 必备的 3-5 项功能）
  - 用户画像（典型用户 + 使用场景）
  - 技术路线（关键决策 + 约束）
  - 边界（明确不做什么）
- **适用**：需开发的软件产品、平台、工具
- **最小示范**：定位"给数据科学家的命令行配置管理器"｜核心"一键切换项目环境"｜画像"同时在 3 个客户项目间切换的咨询顾问"｜路线"Python + pyproject.toml"｜边界"不做 GUI / 不支持 Windows 32 位"
- **何时不适用**：学术研究（无"用户"概念）/ 短平快一次性任务

### 2.2 User Story + BDD · 用户故事与行为驱动

- **来源**：敏捷开发（Agile）+ BDD（Behavior-Driven Development，Dan North 2006）
- **字段结构**：
  - User Story：**As a** [角色] **I want** [动作] **So that** [价值]
  - Acceptance Criteria (BDD)：**Given** [前提] **When** [事件] **Then** [结果]
- **适用**：可分解为一系列用户行为的产品；验收标准需要机械可验证
- **最小示范**：
  - As a 项目管理者 I want 一键生成话题树 So that 能在长会话中保持地图感
  - Given 项目有 ≥3 张 card · When 跑 tree_gen · Then 生成 _tree.md 含 mermaid + ASCII
- **何时不适用**：高度探索性的研究项目（前提/事件/结果无法预先列举）

### 2.3 IMRaD 问题陈述 · 学术

- **来源**：科学写作经典结构（Introduction / Methods / Results / Discussion）改编用于 Vision
- **字段结构**：
  - 问题（本文试图回答什么核心问题）
  - 主张（一句话可说清的核心论点）
  - 读者（谁会读 · 读完带走什么）
  - 边界（不处理什么）
  - 验收画像（定稿时的字数级 / 章节级 / 论证密度画面）
- **适用**：学术论文、方法论文章、理论建构类写作
- **最小示范**：问题"SPDE 框架如何系统性操作化'社会转型'？"｜主张"三层解耦：概念层-范式层-指标层"｜读者"区域科学方法论研究者"｜边界"不重算新旧动能转换争论"｜画像"12000 字，§0-§5，每节 2000 字左右，每 1000 字一个佐证节点"
- **何时不适用**：代码产品 / 数据驱动的实证研究（改用 2.4 或混合骨架）

### 2.4 Jobs to be Done · 用户雇佣

- **来源**：Clayton Christensen（《创新者的窘境》作者）+ Anthony Ulwick 体系化
- **字段结构**：
  - 用户**雇佣**这个产品做什么 job（核心问题）
  - 替代什么旧方案（竞品 / 现有 workflow）
  - 雇佣情境（什么场景下想起雇它）
  - 完成 job 的判据（用户自我评价"做完了"的标志）
- **适用**：需描述**使用动机**而非单纯**功能清单**的产品；颠覆式创新判定
- **最小示范**：Job"在跨会话的复杂项目里不掉线上下文"｜替代"手写入口文档 + 零散笔记"｜情境"连续三天都在改同一论文"｜判据"重启会话后 AI 能秒懂之前卡在哪"
- **何时不适用**：纯研究探索 / 工程内核

### 2.5 Alexander Pattern Language · 模式语言

- **来源**：Christopher Alexander《A Pattern Language》（1977，建筑学）
- **字段结构**：
  - **Context**（情境）：问题发生的场景
  - **Problem**（问题）：核心矛盾 / 冲突
  - **Solution**（解决）：回应该矛盾的通用做法
- **适用**：对"反复出现的问题"沉淀通用解决方案；设计理念类项目
- **最小示范**：Context"AI 在多轮复杂任务中"｜Problem"容易闷头干导致偏题不自知"｜Solution"定期输出'我们在哪'的地图感反馈"
- **何时不适用**：单次性、具体的、无通用性的目标

## §4 · 组合使用

- 同一项目可叠加多个骨架（PRD 做定位 + User Story 做功能 + IMRaD 做内部文档）
- 不同阶段可用不同骨架（早期条目期无骨架 → 中期 PRD → 后期补 BDD 验收）
- 骨架间字段可相互映射（PRD 的"边界" ≈ IMRaD 的"边界" ≈ JTBD 的"不解决的 job"）

不求全而求**适配**。找到最贴合当前项目性质的一个主骨架即可，辅骨架按需加。

## §5 · 自检

每次填完 vision 自问三条：

1. 这份 vision 有没有把"技术执行"冒充为"目标"？（"实现 X"是执行，"用户能用 X 解决 Y"才是目标）
2. 另一个 AI / 人接手时，用这份"产品原型"能少问几个问题？能少 = 够详尽；否 = 还不够
3. 验收时能否无歧义判断"做完了没"？不能 = 仍模糊

自检不过关 → 继续生长 vision。不硬限时间，但不要在 vision 未成型时就开工。
