# 话题生命周期

> ⚠️ **执行规约（非知识文档）**。读完要跑对应脚本，不是只"理解"生命周期。
> **最小执行门**：新话题=`python topic_new.py <项目根> <简称> --parent <ID|null> --root <emoji标签>`；card 填改后=`python check_structure.py <项目根>`；树结构变=`python tree_gen.py <项目根>`。三个动作各对应不同触发，均有流水。
>
> **锚定**：SKILL.md §2.1 话题（§1.1 结构权归用户 · §2.2 记录机制）
> **加载时机**：处理任何话题动作时（新建/讨论/沉淀/收敛/派生任务）。
> **读完即应能**：判断三种卡何时建、何时转状态、何时迁内容、何时收敛。

---

## 1 三位一体

每个话题对应 `topics/NNN_简称/` 一个目录，默认三件套：

| 文件 | 角色 | 性质 |
|:---|:---|:---|
| `scratch.md` | **讨论卡** | 原始讨论过程，时间戳追加，不删不清 |
| `card.md` | **话题卡** | 沉淀认知结论，唯一真理源 |
| `tasks.md` | **任务卡**（可选） | 派生执行层，单动作可省略 |

基础话题卡（`base_topic: true`）可选生成第四组件 `template.md`，承载建构说明、可重复单元模板与地图渲染约定。普通话题需要时通过 `--with-template` 生成。详见 `references/base-topic-templates.md`。

三件套各管不同性质的内容。讨论卡是"过程档案"，话题卡是"结论档案"，任务卡是"执行档案"。**不可混用**——讨论不直接进话题卡（先沉淀再迁），结论不进讨论卡（结论是迁移产物）。

每张卡 frontmatter 的归属字段统一叫 `topic_id`：话题卡是自指，讨论卡和任务卡指向所属话题卡。**独立可读**——脚本或人工读任一文件都不依赖目录推断归属。

## 2 卡片状态

三种卡各有自己的状态流转。状态写在 frontmatter `status` 字段。

### 讨论卡（scratch.md）

```
💭 讨论中  ──共识涌现──▶  🌱 待提炼  ──迁移完成──▶  📦 已封存
```

- **💭 讨论中**：默认初始状态。讨论持续追加，未浮现明确共识。
- **🌱 待提炼**：本次讨论已产生可沉淀的结论，等待迁入话题卡。判定信号：用户说"这个清楚了"/"可以记一下"，或讨论段末尾出现 `🌱 共识：[一句话]`。
- **📦 已封存**：所有结论已迁入话题卡，讨论档案冻结。讨论过程**不删不清**——讨论本身就是数据资产。

### 话题卡（card.md）

```
⏳ 进行中  ──┬──▶  ✅ 已关闭   （讨论清楚且结论采纳）
            ├──▶  ⏸️ 已搁置   （暂无推进条件）
            ├──▶  🔻 已推翻   （结论被反证）
            └──▶  🗑️ 已废弃   （内容有害/错误，仍原地保留）
```

终态选择由用户态度判断。**所有终态物理留 `topics/NNN_简称/` 原地**，不移 archive/，靠 frontmatter `status` 区分。原因：保证引用链不断、git 历史完整、回溯路径清晰。

### 任务卡（tasks.md）

```
⬜ 未开始  ──▶  ⏳ 进行中  ──┬──▶  ✅ 已完成
                            └──▶  ⚠️ 阻塞中  ──▶  ⏳（解除后重入）
```

每次状态变更在 `## 任务日志` 区追加一行 `[YYYY-MM-DD HH:MM] T01 ⬜→⏳ [说明]`。

## 3 新建话题

**触发**：对话中浮现明显偏离当前焦点、值得独立承载的新主题。识别信号：
- 用户原话："我们开个新话题讨论…"/"这个先放一边"/"单独起一个"
- AI 自识别：同一轮出现 ≥2 个 `🌱` 候选且主题正交

**不该独立成话题的信号**（反面判据）：
- 内容是当前话题的子论点或佐证 → 写入当前 card 对应章节（融入，非追加）
- 内容是当前话题的执行步骤 → 写入 tasks.md，不开新话题
- 内容只是一个临时疑问或待查事项 → 写入 scratch 讨论记录，不开新话题
- 拿不准时问用户："这个要独立成话题还是放在当前话题下？"

**该拆分的信号**：
- 一张 card 的 TOC 超过 7 个 H2 章节 → 考虑拆分为多个子话题
- 一段 scratch 讨论同时涉及两个正交主题 → 拆分为两个话题各自讨论

**协商**：先与用户对齐**简称**（2-6 字符中文/小写英文）和 **root 归属**（按当前架构套餐的推荐 root 标签清单，见 `topics/_seeds.md` 或 `init-project.md`）。简称必须能一句话概括话题，否则先澄清再建。

**简称命名示范**：

| 类型 | 正例 | 反例（及修正） |
|:---|:---|:---|
| 长度 | `脚本工具链` · `焦点切换` · `tree-gen` | `项目管理体系的脚本工具链设计和实现` → 改 `脚本工具链` |
| 过短 | `角色库升级` | `改` → 补 `改名规范` |
| 多义 | `命名规则` | `新版` → 补 `新版架构` |
| 特殊字符 | `cache机制` | `脚本/工具` → 去斜杠 `脚本工具` |
| 动宾 | `收敛流程` | 动宾比名词短语更易区分（"收敛" vs "话题收敛流程"） |

长度硬约束：不超过 30 字节（脚本生成路径兼容性保证）。建议 2-6 字符是可读性上限。

**parent 判定**：
- 新主题从属当前焦点 → `parent = 当前焦点 topic_id`
- 否则 → 指向更高层话题，或 `null`（顶层话题，按 root 标签分组）

**执行**：

```
python scripts/topic_new.py <项目根> <简称> --parent <parent_id> --root <根类emoji>
```

脚本产出：
- `topics/NNN_简称/scratch.md`（按 `templates/topic/scratch.md.tmpl` 渲染）
- `topics/NNN_简称/card.md`（frontmatter + TOC 骨架，正文为空）
- 自动调 `tree_gen.py` 重生 `topics/_tree.md`

**初始化**：
1. scratch.md 首条记录添加 `[YYYY-MM-DD HH:MM] 话题初创。[一句话背景/来源]`
2. card.md 在 📑 本卡目录区列出初始 2-3 个章节标题（**仅 TOC，不填正文**）
3. logs/stream.md 追加结构化流水条目（见 SKILL.md §2.2 记录机制：讨论摘要 2-5 句 + 遗留问题 + 切换缘由）

## 4 草场讨论

### 4.0 讨论归属判定

每次讨论开始前判断内容写入哪张 scratch.md：

| 判据 | 归属 |
|:---|:---|
| 与当前焦点 card 同主题（延续、细化、反证其结论） | 当前焦点话题 `scratch.md` |
| 明显属于另一已有话题（扫 `_tree.md` 能锁定） | 该话题 `scratch.md` |
| 新主题（与任何已有话题正交） | 先开新话题（见 §3），再进新 scratch |
| 闲聊 / 确认 / 简单回应 | **不写** scratch，见 §4 末"何时不追加" |

判据冲突时优先"当前焦点"（减少焦点漂移），拿不准就问用户。

### 4.1 追加纪律

讨论卡承载所有原始推演。**最重要的一条规则**：每段以 `[YYYY-MM-DD HH:MM]` 时间戳开头，最新追加在下方，**不覆盖历史**。

**追加格式**：

```markdown
[2026-04-20 14:30] 用户提出 X 观点：……
[2026-04-20 14:35] AI 反面回应：……
> "用户原话引用"
[2026-04-20 14:45] 🌱 共识浮现：……
```

**最佳原话原则**：用户/AI 关键原话以 `> ` 引用嵌入，原话比摘要更能还原语境。优先保留理念、判断、洞察层面的表达。

**何时从 💭 转 🌱**：本段产生可沉淀的明确结论时。判定信号：
- 用户说"这个清楚了"/"可以记一下"/"就这么定"
- AI 自识别：本段已形成完整的论点+依据+结论链
- 段末追加 `🌱 共识：[一句话摘要]`，同步把 frontmatter `status` 从 `💭` 改为 `🌱`

**何时不追加**：本段只是闲聊、确认、简单回应——不污染讨论卡。讨论卡只承载推演内容。

### 4.2 侧写：不切焦点的跨话题更新

> 权威定义见 SKILL.md §1.3 每轮循环，本节补充生命周期视角的示例。

讨论中有时触及另一个话题，但不值得切焦点——只需在那边记一笔。侧写解决严格单焦点假设下跨话题信息丢失的问题。

三个层级（从轻到重）：

| 层级 | 动作 | 示例 |
|:---|:---|:---|
| **只读** | 发现关联但不操作 | "这和 T05 有关，先记着" |
| **侧写** | 在目标话题 scratch 追加简短条目，不切焦点 | 更新状态、补充一条发现、标记待办 |
| **切焦点** | 需要展开讨论或改结构 | 进入目标话题深入推进 |

侧写时保留双向索引：当前话题 scratch 记录 `→ 侧写 NNN：补充了 XX`，目标话题 scratch 记录 `← 来自 NNN/SNNN：XX`。Trace 话题天然是侧写汇聚点——多个话题的进展都可能需要在 Trace 话题上记一笔。

## 5 迁移到话题卡

讨论卡 status 为 🌱 时触发。这是话题生命周期最容易出错的环节，所以**纪律最严**。

### 5.1 禁止追加式写入

**这是话题卡的核心纪律**。内容进入话题卡只有两条路：

1. **骨肉补充**：内容属于已有章节，在该章节的内部逻辑中**融入**
2. **结构重构**：内容不属于任何现有章节，先改 TOC（需用户审批），再迁入新位置

**无论内容是否相关，都不允许在章节末尾追加**。

融入 vs 追加的区别：融入是把内容编织进章节的论述脉络，追加是把内容钉在章节屁股后面。判别标准：移除追加的段落，章节论述是否仍完整？若是 → 那就是追加；若否 → 那是融入。

**结构承载判据**：迁入前先判断新内容与原章节的关系。若它是上层目标、下层步骤、概念定义、例证材料、边界条件或反证材料，就应挂到对应层级；不能因为都与同一话题相关，就把它们写成同级并列段落。

### 5.2 TOC 与正文严格对齐

新版话题卡以 frontmatter `toc:` 为唯一结构源，正文 `## 📑 本卡目录` 是 `card_write.py` 自动渲染的只读视图。TOC 条目格式：

```yaml
toc:
  - "1 标题 | 本节承载什么内容"
  - "1.1 子标题 | 本小节承载什么内容"
```

约束：

1. frontmatter toc 条目与正文 `## N 标题` / `### N.M 标题` 序号、标题、层级一一对应
2. `|` 后的 intent 是语义锚，AI 写入前必须确认内容属于该章节 intent
3. 正文 `📑 本卡目录` 不手写修改；需要改结构时先改 frontmatter toc，经用户审批后由脚本重渲染
4. 结构变更必须**用户审批**（AI 提议 → 用户批准 → 才能改 TOC + 正文）

校验脚本：

```
python scripts/check_structure.py <项目根> --card NNN_简称
```

### 5.3 迁移流程

1. 从讨论卡抽取 🌱 段对应的核心结论 + 最佳原话
2. 先把结论改写为对象结构表述：讨论卡可以保留“问题—回应—修正”的过程链；迁入 card 时只继承其中已成立的结构、机制、边界和结论，正向说明对象是什么、如何运作、为何这样组织。
3. 判定该结论对应话题卡哪个 TOC 条目：
   - **已存在** → 用 `card_write.py --section <N> --mode integrate|replace --content-file <path>` 写入对应章节；脚本会校验 section 是否在 frontmatter toc 中，并输出 intent 语义锚（写入前自问：移除这段后该章节论述是否仍完整？是→追加，违纪；否→融入，合规）
   - **不存在** → AI 提议新增 `§N [新标题]` + intent + 理由 → `card_write.py --mode restructure --approval pending` → 等用户审批（沉默=拒绝）→ 批准后同步改 frontmatter toc + 正文
4. 用户否决新章节提议 → 保持讨论卡不动，标记"待结构审查"
5. 在对应讨论卡段末尾追加 `→ card §N`（标记已迁移）
6. 更新话题卡 frontmatter `updated` 为当前时间戳

### 5.4 结构权 vs 内容权

| 权限 | AI 可做 | AI 不可做 |
|:---|:---|:---|
| **结构** | 提议（frontmatter toc 调整 / 分章重组 / 新开话题） | 直接改（须用户审批） |
| **内容** | 填充（章节正文 / 论证 / 引用） | — |

**重摆不重写**：审批通过的结构调整只搬位置，不重新生成内容。内容够好就搬家。

## 6 话题收敛

话题卡承载完整结论且无新讨论时触发。识别信号：
- 用户原话："这个话题就到这里"/"可以关了"/"搁置吧"
- 讨论卡所有 🌱 段都已标 `→ card §N`

**终态选择**：

| 场景 | 终态 |
|:---|:---|
| 讨论清楚且结论采纳 | ✅ 已关闭 |
| 暂无推进条件 | ⏸️ 已搁置 |
| 结论被反证/推翻 | 🔻 已推翻 |
| 内容有害/错误 | 🗑️ 已废弃 |

**执行**：
1. 修改话题卡 frontmatter `status` 为选定终态 emoji
2. 修改讨论卡 frontmatter `status` 为 `📦 已封存`
3. 调 `tree_gen.py` 重生 `_tree.md`（脚本自动重算节点颜色）
4. **物理不移 archive**——所有终态留 `topics/NNN_简称/` 原地
5. 流水追加收敛行

### Vision 联动检查

> 反向审查判据的权威定义见 `references/review-ops.md` §2.2。本节为正向检查（话题收敛→Vision/Structure），与 review-ops 的反向检查判据对称。

收敛时（特别是 ✅ 关闭的重要话题）检查本卡结论是否影响 **Vision 基础话题卡**（承载项目方向与验收标准）。三条判据：

- **新核心概念**：本卡引入 Vision 卡里没有的核心概念？
- **推翻/挑战**：本卡推翻 Vision 卡的某主张？
- **细化**：本卡细化 Vision 卡的某部分？

任一条命中 → 提示用户更新 `doc/Framework/Vision/Vision.md`，必要时同步入口索引。这是**线索触发**，不是每次必查。

### Structure 联动检查

**Structure 基础话题卡**（承载内容骨架）发生变更时，检查已有话题卡的章节归位是否仍然成立。三条判据：

- **章节消失**：Structure 卡删除或合并了某骨架节点，已有话题卡的归位目标是否失效？
- **层级调整**：Structure 卡调整了骨架层级关系，已有话题卡的 parent/root 是否需要跟调？
- **新增骨架**：Structure 卡新增节点，已有话题卡中是否有内容应迁入新位置？

任一条命中 → 提示用户审查受影响的话题卡。同样是线索触发。

## 7 任务派生

话题卡结论包含明确的执行性子步骤时考虑建任务卡。

**判定**：
- 是否有 ≥2 个需独立跟踪的执行单元？是 → 建 tasks.md；否 → 直接在话题卡处理
- 每个任务是否可量化产出（"写完某脚本"/"交付某文件"）？是 → 有资格作 task；否 → 归回讨论性话题
- 任务间有依赖 → 用 `依赖：T01` 字段表达

**执行**：按 `templates/topic/tasks.md.tmpl` 渲染生成。列出 T01、T02… 每项含状态、依赖、产出路径、说明。

**任务焦点**：全局 focus 只锚定话题；若用户要推进某具体任务，在该话题 `tasks.md` 中标记任务状态，旧 `NNN:TMM` 只作读取兼容。

### 7.1 Trace 话题 vs tasks.md 边界

tasks.md 是话题内部的待办清单（"这个话题里还有哪几步没做"），Trace 话题是独立话题（"这个问题需要自己的讨论空间"）。三个触发条件满足任一即开 Trace 话题：

1. 问题需要**多轮诊断**而非单步执行
2. 问题**跨越多个话题**需要协调
3. 问题需要记录完整的"发现→分析→方案→验证"链条

Trace 话题使用常规 root 标签（按 `_seeds.md` 选取），其追踪性质由话题命名和功能体现。项目初始化时自动建立的 Trace 基础话题卡（`base_topic: true`）是默认追踪枢纽（见 SKILL.md §3.2 初始化）。

## 8 卡片间引用

话题卡 🔗 链接区使用 Obsidian 风格 `[[NNN_简称]]`。示例：

```markdown
- **父**：[[100_项目管理]]
- **子**：[[112_脚本工具链]] · [[113_可视化]]
- **相关**：[[004_流程优化]]
```

`check_links.py` 校验所有 `[[]]` 链接的有效性。

## 9 何时该如何，速查

| 情境 | 动作 |
|:---|:---|
| 用户提的是新主题 | 第 3 节·新建话题 |
| 用户在讨论当前焦点 | 第 4 节·草场讨论（追加时间戳段） |
| 讨论出现共识 | 标 `🌱 共识`，转 status |
| 用户说"沉淀一下" | 第 5 节·迁移到话题卡（走 `card_write.py`，守 §5.1 禁止追加） |
| 话题卡结构不够用 | 第 5.4 节·提议重构等审批 |
| 话题没新内容了 | 第 6 节·收敛（选终态，留原地） |
| 话题里要做事 | 第 7 节·任务派生（≥2 个再建 tasks.md） |
