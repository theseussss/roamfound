# 审查机制

> ⚠️ **执行规约（非知识文档）**。审查必调脚本（结构=`check_structure.py`，断链=`check_links.py`），AI 不凭印象判对齐。
> **最小执行门**：card 填改后 / 脚本告警 → `python check_structure.py <项目根> [--card NNN]` + `python check_links.py <项目根>` → 告警清零或落 CLAUDE.md §待解决 → 写流水。**禁止自动全扫**（token 成本）。
>
> **锚定**：SKILL.md §4 审查（§2.1 话题 TOC 对齐）
> **加载时机**：用户要求反向审查 vision 变更影响、结构审查话题卡、或脚本告警触发时。
> **读完即应能**：区分按需触发与自动扫描、守审批门、用正确方式提议重摆。

---

## 1 两种审查场景

| 审查 | 目标 | 触发方式 |
|:---|:---|:---|
| **反向审查** | Vision / Structure 基础话题卡变更后检查下游话题是否仍对齐 | 用户主动 / AI 顺便发现 |
| **结构审查** | 话题卡 TOC 与正文对齐、层级均衡 | 脚本告警 / AI 填卡发现 / 用户主动 |

**核心纪律**：两种审查**都不自动全扫**。原因：token 成本意识——全扫所有话题的判断成本远高于按需触发。

---

## 2 反向审查

### 2.1 触发模式

反向审查锚定在两张基础话题卡上：**Vision 卡**（方向与验收标准）和 **Structure 卡**（内容骨架）。两张卡变更后都可能导致下游话题失效。

只有两种合法触发：

**模式 A 用户主动**：
- 原话："Vision 改了，子话题检查一遍"/"Structure 调了骨架，看看受影响的 card"
- 用户指定范围（"所有 parent=100 的 card"/"关于 X 主题的"）

**模式 B AI 线索**：
- AI 在**推进某具体子话题**的过程中**顺便发现**该子话题与最新 Vision / Structure / 上游 card 存在冲突
- 立刻中断当前动作，提示"本话题可能受 Vision/Structure 变更影响"

**禁止**：AI 自主发起大范围扫描（"让我检查所有话题是否还对齐"——违反 token 成本意识）。

### 2.2 判定标准

**Vision 变更判据**（与话题收敛 Vision 检查的反向版本，见 `topic-lifecycle.md` §6）：

- 话题卡结论与 Vision 卡某主张矛盾？
- Vision 卡某主张已不再支持本卡的推论链？
- Vision 卡新概念应该在本卡体现却没有？

**Structure 变更判据**：

- Structure 卡删除或合并了某骨架节点，本卡归位目标是否失效？
- Structure 卡调整了层级关系，本卡的 parent/root 是否需要跟调？
- Structure 卡新增节点，本卡中是否有内容应迁入新位置？

### 2.3 执行

**模式 A**：
1. 用户指定范围
2. AI 顺序读对应话题卡，对每张按判据比对 Vision / Structure 卡
3. 冲突清单：`[[NNN_简称]] · 冲突点：…`
4. 用户逐张决策：修话题卡 / 修 vision / 维持不动
5. 流水追加 `[~修改 | discovery | 共识] 反向审查 [[NNN_简称]]：[结论]`

**模式 B**：
1. AI 在推进中说："💡 注意——本话题结论与 vision 第 N 条可能冲突。是否先处理？"
2. 用户决策：立即处理 → 切入修改流程；延后 → 在当前话题卡末尾加脚注 `Vision/Structure 冲突：待处理`

## 3 结构审查

### 3.1 触发

- `scripts/check_structure.py` 输出问题报告
- `scripts/health_check.py` 在 dashboard 亮"结构警告"
- AI 在填话题卡时发现 frontmatter toc 与正文已偏离
- 用户主动："这个卡结构乱了，重排一下"

### 3.2 判定

- frontmatter toc 条目与正文 `## N 标题` / `### N.M 标题` 是否一一对应（序号、标题、层级严格一致）？
- `📑 本卡目录` 是否只是 frontmatter toc 的只读渲染，没有被手写改成另一套结构？
- 同级并列条目是否 >7？（触发拆分提示）
- 层级是否均衡？（某章节子项远多于其他 → 建议重组）

### 3.3 执行

```
python scripts/check_structure.py <项目根> --card NNN_简称
```

获取问题清单后：

1. AI **提议**重整方案（前后对比）：

   ```
   当前结构：§1 A  §2 B  §3 C (其下 7 条并列)  §4 D
   提议重整：§1 A  §2 B  §3 C  §4 D
             (§3 C 原 7 条拆为 §3.1-§3.3 + §4' 新章节)
   理由：并列>7 触发拆分原则；拆分后逻辑更清
   ```

2. **等用户审批**（沉默不代表同意）：
   - 通过 → AI 执行**重摆**（改 frontmatter toc 条目顺序/层级、重渲染 📑 目录、迁移正文章节块），**不重写内容**
   - 拒绝 → 保持原状，话题卡脚注加一行 `[YYYY-MM-DD] 结构审查：用户选择维持`

3. 重摆完成后再次调 `check_structure.py` 校验
4. 流水追加 `[~重构 | decision | 落地] [[NNN_简称]] 结构重摆 §N→§M（内容不变）`

---

## 4 重摆不重写

结构审查最核心的纪律：**只搬位置，不重新生成内容**。

- 允许：改 frontmatter toc 条目顺序、调整章节层级、重渲染 📑 本卡目录、在正文内迁移章节块
- 禁止：用"重整"名义重新写某章节的正文
- 判别：重摆前后内容字节数基本不变（可能因标题改动微差）

理由：重摆是在结构层调整，内容已经是用户审批过的。重新生成相当于绕过了"内容权归 AI、结构权归用户"的分工——等于 AI 借结构审查之名改了内容。

---

## 5 结构权归用户

审查发现的问题**不等于**审查者自动修改的授权。AI 的权限是：

| 动作 | AI 是否可做 |
|:---|:---|
| 扫描问题 | ✅（脚本辅助） |
| 提议方案 | ✅（明确标注"建议"） |
| 等用户决策 | ✅（沉默=拒绝） |
| 直接修改结构 | ❌ |
| 重写内容借口"重整" | ❌ |

这是整个 skill 的核心分工的一部分，见 SKILL.md §1.1 总纲（结构权归用户）+ §2.1 话题（三件套的建、改规则）。

---

## 6 何时不审查

以下情况**不启动**审查流程：

- 话题卡结构目前够用但不完美——让时间去检验是否真需要重整
- 个别话题卡轻微偏差但无明显问题——健康检查报告会累积告警，到阈值再统一处理
- 用户没要求且 AI 没发现线索——主动扫描是违纪的

审查是**按需机制**，不是例行公事。
