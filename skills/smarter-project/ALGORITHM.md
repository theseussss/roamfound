# smarter-project 算法框架

> 本文件是 SKILL.md 重写的设计依据。描述 skill 的完整行为算法，不含实现细节。

## 设计原则

- 状态全在 md 文件，打开编辑器即可审计
- 脚本做操作，AI 做判断
- 焦点检查是核心引擎，其他动作围绕它运转
- hooks 充当轻量中介层（读写对 AI 透明），未来演进为 MCP/GUI

## SESSION START

```
用户首条消息
     │
     ▼
判断任务复杂性
├─ 简单问答 → 无项目行为，直接回答
└─ 需要建档 ↓

项目存在吗？
├─ 不存在 → init 脚本
│  ├─ 选套餐（学术/实证/代码/短平快）
│  ├─ 建目录结构
│  ├─ 建基础话题卡集（Vision/Structure/Style/Trace）
│  └─ 建对应空 doc（话题是厨房，doc 是出菜口）
│
└─ 已存在 → 全套体检脚本
   ├─ 扫描结构合规性
   ├─ 检查三件套完整性
   └─ 报告 + 规范化建议

读 AGENTS.md → 读 `.jiacong/focus.json` → 建焦点面包屑 → 输出首段
```

## EVERY TURN（核心循环）

```
用户消息
     │
     ▼
① 焦点检查（由 UserPromptSubmit hook 触发：注入焦点 + 流水状态；AI 据此判断话题是否切换）

   本轮消息还是同一话题？
   ├─ 是 → 输出短面包屑，继续当前话题
   ├─ 触及其他话题但不值得切焦点 → 侧写（三级）
   │  ├─ 只读：发现关联，不操作
   │  ├─ 侧写：在目标话题 scratch 追加简短条目，不切焦点
   │  └─ 切焦点：需要展开讨论或改结构
   └─ 否（新话题浮现 / 用户指定）
      ├─ AI 自信 → 直接建话题 + 切焦点
      ├─ AI 不自信 → 提议，等用户确认
      └─ 用户说暂不 → 标记，不切焦点
         （下轮若用户追问新话题内容 → 自动识别切换）
     │
     ▼
② 角色确认：视角一以贯之

   已有角色 → 保持（除非话题域变了）
   需要角色 → 选/建，蒸馏该领域最强大脑
   无角色   → 也是选择（更开放但可能更平庸），坦诚声明
     │
     ▼
③ 执行回复

   读规则 → 跑脚本（如需）→ 输出
     │
     ▼
④ 写 scratch（每轮必做）

   当前话题的 scratch.md 追加带编号的条目
   如本轮产出了额外文件 → 在 scratch 中索引
```

## 话题生命周期

### 话题开启（含新建 + 从其他话题切入）

```
脚本建三件套（新建时）/ 加载已有三件套（切回时）
在 log 预写一条开放条目
格式：[时间] 开启/切入 NNN_简称 ...
```

### 话题切换（= 旧话题签退 + 新话题签到）

```
旧话题：
├─ 读 scratch → 汇总摘要
└─ 补完 log 中旧话题的开放条目

新话题：
├─ 在 log 预写新的开放条目
├─ 更新 .jiacong/focus.json（旧 .claude/focus 只作 fallback mirror）
└─ 输出焦点切换警告（如旧话题未完成）
```

### 话题关闭

```
读 scratch → 终结摘要 → 补完 log
status 流转到终态
```

### 话题文件夹结构

```
topics/NNN_简称/
├── card.md        结构化结论（唯一真理源）
├── scratch.md     讨论过程（带编号条目 + 额外文件索引）
├── tasks.md       执行步骤（可选）
└── *.md / *.xxx   额外文件（诊断/方案/草稿等）
                   必须在 scratch 中以编号索引
```

## 四种记录机制的分工

```
              Trace话题             tasks.md           log                scratch
──────────────────────────────────────────────────────────────────────────────────
导向          任务导向              执行导向            时间线导向            过程导向
粒度          需求/bug/修订单       话题内待办项        话题级签到签退         每轮条目
内容          修什么、为什么修、     具体步骤            讨论摘要 +           讨论了什么、
             改了什么、验收结果     完成/未完成          切换缘由              推导了什么
类比          issue tracker        todo list          git log --oneline    git diff
读者          "这个问题解决了没"    "这一步做了没"      "项目经历了什么"      "当时怎么想的"
写入时机       任务产生/推进/       任务产生/推进时      话题切换/关闭时        每轮回复后
             关闭时
归属          独立话题              话题内部            项目级                话题内部
```

Trace（追踪）话题 vs tasks.md 边界：tasks.md 是话题内部待办清单；Trace 话题是独立话题。
三个触发条件满足任一即开 Trace 话题：①多轮诊断 ②跨话题协调 ③完整链条记录需求。

## 初始化：基础话题卡集

四张基础话题卡跨套餐统一命名（frontmatter 标记 `base_topic: true`），内容随套餐差异化：

```
话题层（活的工作区）             doc 层（阶段性快照）
┌────────────────────┐        ┌──────────────────┐
│ Vision              │ ─────▶ │ doc/vision.md     │
│ （方向：做什么、为谁）│        │                  │
├────────────────────┤        ├──────────────────┤
│ Structure           │ ─────▶ │ doc/structure.md  │
│ （骨架：内容怎么组织）│        │                  │
├────────────────────┤        ├──────────────────┤
│ Style               │ ─────▶ │ doc/style.md      │
│ （表达：用什么方式说）│        │                  │
├────────────────────┤        ├──────────────────┤
│ Trace               │ ─────▶ │ doc/trace.md      │
│ （过程：经历了什么）  │        │                  │
└────────────────────┘        └──────────────────┘
```

名称统一，承载内容按套餐不同：学术套餐的 Vision = 项目理想样态+验收标准，
代码套餐的 Vision = 产品定位+核心能力；Structure 在学术=论文结构地图，
在代码=codemap；以此类推。

## 角色机制

- **理念**：视角应当一以贯之。成为高手的最佳方式是模仿高手、蒸馏高手
- **无角色也是角色**：更开放、普适，但可能更平庸
- **选角**：根据任务选取，调用对应参数的最强大脑，借鉴顶尖人类角色作为资源
- **诚实**：如果 AI 没有信心扮演好某角色，应当坦诚声明
- **七列必填**：角色/代表人物群/经验/思考框架/见过的失败/盲区/适用场景
- **双层库**：项目库（当前项目）+ 全局库（跨项目共享）

```

│ dashboard.html    │    │ MCP server       │    │ 统一 GUI          │
```

hooks 在当前阶段充当轻量中介层：
- `user_prompt_submit` hook：自动注入 focus + breadcrumb
- `assistant_response` hook：自动触发 scratch 写入检查
- 文件仍是真理源，hooks 让读写对 AI 透明
